# DailySpeak 项目文档

本目录是项目的**唯一信息源**。需求、决策、排期都只在这里维护，不再散落在聊天记录或某个人脑子里。

## 目录地图

| 文件 | 作用 | 什么时候改它 |
| --- | --- | --- |
| [`prd/PRD.md`](./prd/PRD.md) | **需求权威来源**。产品要做什么、口径怎么定，一切以它为准 | 新增功能 / 调整口径 / 变更范围时，**先改这里** |
| [`prd/archive/`](./prd/archive/) | 历史存档（v0.1 原始 PRD HTML） | 只读，永不修改 |
| [`DECISIONS.md`](./DECISIONS.md) | 决策记录（ADR）。每条决策的背景、结论、影响 | 做了决策 or 推翻旧决策时 |
| [`TODO.md`](./TODO.md) | 待办 + 排期 + 待确认清单，勾选式 | 有新任务、完成一项、需要人确认时 |

## 三条硬规则

### 规则 1：PRD 是主参考，新功能必须先写进 PRD

任何新功能、新口径，**流程固定为**：

```
需求出现
  → 先更新 prd/PRD.md（写清新功能的页面布局 / 业务逻辑 / 边界异常 / 数据模型影响）
  → 在 PRD 的「变更记录」表里加一行
  → 再到 TODO.md 登记为待办
  → 才开始写代码
```

不允许「代码先写完再补文档」。PRD 里没有的东西，就不算需求。

新增内容在 PRD 里用 `【v0.2】` 这类版本标记标出，下一版改成 `【v0.3】`，方便对照。

### 规则 2：排期与待确认，一律进 TODO.md

- 所有要做的事都在 [`TODO.md`](./TODO.md)，**做完一项就把 `[ ]` 改成 `[x]` 并写上日期**。
- 需要人拍板或提供东西的，放进 `A. 待你确认` / `B. 需要你提供的凭证` 两个区，并用 🔴 / 🟡 标出阻塞程度。
- 中途冒出来的新任务，同样先补 PRD，再在 TODO 里加一条；**不要口头记着**。

### 规则 3：决策进 DECISIONS.md，编号不复用

- 每条决策一个编号 `D-xxx`，写清 **背景 / 决策 / 影响**。
- 决策变了不改旧条目，而是新增一条并注明「取代 D-xxx」，旧条目标成 `已废弃`。
- 状态只有三种：`已定` / `待确认` / `已废弃`。
- **待确认的决策必须在 TODO 的 A 区有对应待办**，确认后两边同步更新：这里改状态与结论，TODO 里勾掉。

## 三者怎么互相引用

```
TODO 条目   ──→  DECISIONS 的 D-xxx（这个任务为什么要做）
PRD 章节    ──→  DECISIONS 的 D-xxx（这条口径是怎么定的）
DECISIONS   ──→  PRD 章节 + TODO 条目（这个决策影响哪些需求、产生哪些任务）
```

引用时用相对链接，例如 `→ [D-014](./DECISIONS.md#d-014-仓库目录结构待确认)`。
