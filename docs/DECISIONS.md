# 决策记录（ADR）

记录本项目所有**已定**与**待确认**的决策。目的：避免同一个问题反复讨论，也让后来的人知道「为什么是这样」。

## 怎么用

1. **只增不改**：每条决策一个编号，编号永不复用。决策发生变化时，新增一条并注明「取代 D-xxx」，旧条目标记为 `已废弃`。
2. **状态三种**：`已定` / `待确认` / `已废弃`。
3. **待确认的决策，在 [`TODO.md`](./TODO.md) 的「待你确认」区有对应待办**。用户确认后，两边一起更新（这里改状态与结论，TODO 里勾掉）。
4. **决策涉及需求口径的，必须同步更新 [`prd/PRD.md`](./prd/PRD.md)**，并在 PRD 的变更记录里登记。
5. 条目里写清三件事：**背景**（为什么要想）、**决策**（定了什么）、**影响**（会改变什么）。

## 已定

### D-001 样式方案采用 Tailwind v4

- **日期**：2026-09-11
- **背景**：项目使用了 Tailwind 工具类，设计稿（`design/pages/*.html`）靠 `@tailwindcss/browser` CDN 渲染，但工程侧从未安装 Tailwind，导致所有页面样式塌陷（登录页居中布局失效、间距全丢）。
- **决策**：接入 `tailwindcss@4` + `@tailwindcss/vite`，在 `src/styles/tokens.css` 顶部 `@import 'tailwindcss'`，并用 `@theme inline` 把语义 token 映射成工具类（`text-muted-foreground` 等），与设计稿写法保持一致。
- **影响**：工具类与设计稿对齐；设计 token 仍是唯一颜色来源；新增页面直接沿用现有 class 约定。
- **依据**：工程实际故障排查；设计稿实现方式。

### D-002 登录页采用字段级内联校验

- **日期**：2026-09-11
- **背景**：原实现只有一个表单级错误框，账号为空或格式不对时会走到后端并提示「账号或密码不正确」，误导用户；PRD 5.1 要求「密码强度不足内联报错」。
- **决策**：账号格式、密码强度、两次密码一致各自独立校验，错误定位到具体输入框（红框 + 字段下方文案），并带 `aria-invalid` / `role="alert"`；用户重新输入时清除该字段错误；服务端错误仍在表单底部统一呈现。
- **影响**：登录/注册体验与可访问性提升；`isEmailOrPhone` / `isStrongPassword` 从 service 导出供表单复用。
- **依据**：PRD 5.1「边界与异常」。

### D-003 密码强度规则对齐 PRD

- **日期**：2026-09-11
- **背景**：PRD 字段规则写「≥ 8 位，大小写字母 + 数字」，但实现只校验「字母 + 数字」，文案与实现不一致（文案声称要大小写，实际不校验大写）。
- **决策**：以 PRD 为准，`isStrongPassword` 要求 ≥ 8 位且同时包含小写字母、大写字母、数字；提示文案同步精确化。
- **影响**：注册门槛略升；占位符与错误文案需保持一致。
- **依据**：PRD 5.1「字段规则」。

### D-004 今日任务采用当天快照

- **日期**：2026-09-11
- **背景**：原实现每次进入学习台都重新计算今日任务。完成一张复习卡后该卡不再到期，`新句名额 = 每日条数 − 到期复习数` 随之变大，导致今日条数在一天内从 3 变 4，进度显示跳变；只完成跟读就离开的卡会从列表消失且没有复习排期，等于永久丢失。
- **决策**：当天首次进入学习台时生成任务快照并落库（`today_plan`，唯一键 `(user_id, date_key)`），当天固定不变。快照生成时：到期复习卡全部纳入；跟读已完成、应答未完成的卡优先补回；再从未学过的卡里按领域随机补足名额（排除已到期复习卡，避免重复）。用户改领域或每日条数后快照作废重建。
- **影响**：进度显示稳定；中断的卡不会丢；需要一张 `today_plan` 表（PRD 07 章已补充）。
- **依据**：PRD 5.3 `[v0.2]`。

### D-005 完成口径：跟读 + 应答都完成才算一条

- **日期**：2026-09-11
- **背景**：原实现只要产生过进度记录（即完成跟读）就计入「已完成」，进度虚高；且复习卡因为带着上一次学习的分数，一进页面就显示「跟读 ✓ 应答 ✓」。
- **决策**：`已完成 = 跟读分与应答分都存在，且本轮提交发生在今天`。步骤标记同样只看今天的提交。
- **影响**：学习台进度真实反映当天成果。
- **依据**：PRD 5.4 状态流转「已掌握」。

### D-006 复习排期一次只推进一级

- **日期**：2026-09-11
- **背景**：跟读与应答分两步提交，原实现两步各自触发一次排期计算，一次复习会让卡片连跳两个遗忘曲线阶段（S2 → S4），曲线失真；且排期依据取跟读/应答的较大值，与 PRD 的口径不符。
- **决策**：排期只在「整卡完成」（应答打分）时推进一次；推进/回退依据**综合分**（跟读 × 0.5 + 应答 × 0.5），阈值 `PASS_THRESHOLD = 85`。
- **影响**：跟读阶段只记分不改排期；中断在跟读阶段的复习卡仍保持到期状态，会重新出现在今日任务里。
- **依据**：PRD 5.5。

### D-007 录音回听用本地 object URL 并交接给结果页

- **日期**：2026-09-11
- **背景**：用户可以录音但无法回听自己的发音，`useRecorder.stop()` 拿到的音频 blob 被直接丢弃。
- **决策**：录音结束后生成 `objectURL` 供页面回放（播放/暂停，暂停回起点）；跳转到结果页时把该 URL **交接**过去（交接后不在学习页卸载时回收），使用户能对照 AI 反馈复听；重新录音时回收上一段。回放与浏览器 TTS 互斥，避免叠音。
- **影响**：满足「口语复盘」场景；音频的**持久化**是另一个问题，见 D-017。
- **依据**：PRD 5.4 `[v0.2]` 录音回听。

### D-008 跟读评分 100% 由词级相似度决定

- **日期**：2026-09-11
- **背景**：原跟读分只由录音时长推算（越接近「标准时长」分越高）再加 ±6 分随机抖动，**与用户实际说了什么完全无关**；反馈文案是拿分数套模板生成的，会输出「「my experience.」的尾音偏弱」这种与实际发音无关的内容。
- **决策**：按 PRD 06 章口径，跟读分完全由 ASR 转写与原句的词级相似度决定（权重 100%）。算法：归一化 → LCS 词级对齐 → `相似度 = 正确词数 / 原句词数` → `分数 = clamp(round(52 + 相似度 × 46), 40, 98)`。反馈必须由 diff 生成，指出具体是哪些词漏读或被听成了什么。
- **影响**：没有转写结果时无法给出跟读分（不得用随机数顶替），按 09 章降级为「只记完成、不打分」。
- **依据**：PRD 06 章「评分维度与口径」；用户明确要求移除模拟评分。

### D-009 学习页回显 ASR 转写并逐词对照

- **日期**：2026-09-11
- **背景**：用户希望知道「自己说的内容转成英文文本后是否正确」——这是区分「识别错」与「自己读错」的唯一依据，也是发音反馈可信度的前提。
- **决策**：录音结束后展示「我听到的」卡片：转写全文 + 转写来源标识 + 逐词对照原句（错误词红色波浪线，悬停显示被听成了什么）+ 词级准确度百分比。情境应答无唯一原文，只回显文本不做对照。转写失败按 09 章降级，**不允许用本地模拟文本顶替**。
- **影响**：跟读评测接口必须返回 `transcript` / `transcriptSource` / `alignment` / `similarity`；对齐算法在后端实现，前端只渲染。
- **依据**：用户需求；PRD 06 章 `[v0.2]` 接口返回契约。

### D-010 移除全部 mock 数据，按 PRD 做真实实现

- **日期**：2026-09-11
- **背景**：当前工程没有任何后端：登录态、内容库、进度、排期、评分、转写全部由 localStorage 与前端模拟逻辑提供（`services/api.ts`、`data/cards.ts`、`services/scoring.ts`、`services/asr.ts` 的 `mockTranscript` 等）。仅能演示，不可用。
- **决策**：**彻底移除所有 mock**。按 PRD 08 章实现真实架构：Supabase（Auth + Postgres）+ NestJS 后端 + Prisma + 真实 ASR/LLM 供应商。前端不再包含任何假数据、假延迟、假分数、假转写。
- **影响**：这是一次涉及前后端的数据层重写，需要分期实施（见 [`TODO.md`](./TODO.md) P0–P4）；需要用户提供 Supabase 与 AI 供应商凭证。
- **依据**：用户明确指令。

### D-011 ASR 与 LLM 只在后端调用

- **日期**：2026-09-11
- **背景**：前端曾用浏览器 `SpeechRecognition` 获取真实转写，并用本地模拟转写兜底。这既不符合 PRD 06 章的评测链路（ASR 在后端），也无法保证一致性与可审计性；且浏览器识别在部分网络环境不可用。
- **决策**：前端只负责采集音频并上传；ASR 与 LLM 均由 NestJS 后端调用，供应商以 `AsrProvider` / `LlmProvider` 接口注入。前端删除 `useTranscriber`，`services/asr.ts` 的模拟转写与错词表一并删除，词级对齐算法下沉到后端。
- **影响**：供应商密钥不进入前端；切换供应商不影响业务逻辑；前端需处理上传、超时与降级。
- **依据**：PRD 06 章评测链路、08 章技术架构。

### D-016 参考音频方案（待确认）

- **背景**：学习页的「重听原声」目前用浏览器自带 TTS（`SpeechSynthesis`），音色随操作系统变化、不可控，且无法保证与文本一致的质量。PRD 未明确规定参考音频来源。
- **选项**：
  - **A. 保留浏览器 TTS**：零成本、零延迟，但音色不可控、不同设备体验不一致。
  - **B. 服务端 TTS 预生成**：内容上线时用 TTS（如 CosyVoice / 火山 TTS）生成参考音频存 Supabase Storage，前端用 `<audio>` 播放。音色统一可控，成本是每条内容一次合成与少量存储。
- **倾向建议**：B。既然内容由后端管理且要人工审核，「原声」也应由内容库一起产出，这样「跟读原声」才成立。

### D-017 音频是否落库（待确认）

- **背景**：录音默认只在浏览器内存里（D-007）。若要把用户录音持久化，可上传 Supabase Storage，从而支持历史记录里回听自己的发音。
- **选项**：
  - **A. 不落库**：只在本会话内回听，上传后即丢弃。隐私风险最低、存储零成本。
  - **B. 落库**：历史可回听，但涉及隐私合规、存储成本与生命周期管理。
- **倾向建议**：A。MVP 阶段回听的需求在「复盘当下这一次」而非「回听一个月前」，B 可在二期评估。
