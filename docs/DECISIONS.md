# 决策记录（ADR）

记录本项目所有**已定**与**待确认**的决策。目的：避免同一个问题反复讨论，也让后来的人知道「为什么是这样」。

## 怎么用

1. **只增不改**：每条决策一个编号，编号永不复用。决策发生变化时，新增一条并注明「取代 D-xxx」，旧条目标记为 `已废弃`。
2. **状态三种**：`已定` / `待确认` / `已废弃`。
3. **待确认的决策，在 [`TODO.md`](./TODO.md) 的「待你确认」区有对应待办**。用户确认后，两边一起更新（这里改状态与结论，TODO 里勾掉）。
4. **决策涉及需求口径的，必须同步更新 [`prd/PRD.md`](./prd/PRD.md)**，并在 PRD 的变更记录里登记。
5. 条目里写清三件事：**背景**（为什么要想）、**决策**（定了什么）、**影响**（会改变什么）。

> 编号不连续是正常的：决策一旦定下就保留原编号并换区，不重新编号。

## 已定

### D-001 样式方案采用 Tailwind v4

- **日期**：2026-09-11
- **背景**：项目使用了 Tailwind 工具类，设计稿（`design/pages/*.html`）靠 `@tailwindcss/browser` CDN 渲染，但工程侧从未安装 Tailwind，导致所有页面样式塌陷（登录页居中布局失效、间距全丢）。
- **决策**：接入 `tailwindcss@4` + `@tailwindcss/vite`，在 `src/styles/tokens.css` 顶部 `@import 'tailwindcss'`，并用 `@theme inline` 把语义 token 映射成工具类（`text-muted-foreground` 等），与设计稿写法保持一致。
- **影响**：工具类与设计稿对齐；设计 token 仍是唯一颜色来源。

### D-002 登录页采用字段级内联校验

- **日期**：2026-09-11
- **背景**：原实现只有一个表单级错误框，账号为空或格式不对时会走到后端并提示「账号或密码不正确」，误导用户；PRD 5.1 要求「密码强度不足内联报错」。
- **决策**：账号格式、密码强度、两次密码一致各自独立校验，错误定位到具体输入框（红框 + 字段下方文案），带 `aria-invalid` / `role="alert"`；重新输入时清除该字段错误；服务端错误仍在表单底部统一呈现。
- **影响**：`isEmailOrPhone` / `isStrongPassword` 从 service 导出供表单复用。

### D-003 密码强度规则对齐 PRD

- **日期**：2026-09-11
- **背景**：PRD 字段规则写「≥ 8 位，大小写字母 + 数字」，实现只校验「字母 + 数字」，文案与实现不一致。
- **决策**：以 PRD 为准，要求 ≥ 8 位且同时包含小写字母、大写字母、数字；提示文案同步精确化。

### D-004 今日任务采用当天快照

- **日期**：2026-09-11
- **背景**：原实现每次进入学习台都重新计算今日任务。完成一张复习卡后该卡不再到期，`新句名额 = 每日条数 − 到期复习数` 随之变大，今日条数在一天内从 3 变 4，进度跳变；只完成跟读就离开的卡会从列表消失且没有复习排期，等于永久丢失。
- **决策**：当天首次进入学习台时生成任务快照并落库（`today_plan`，唯一键 `(user_id, date_key)`），当天固定不变。生成时：到期复习卡全部纳入；跟读已完成、应答未完成的卡优先补回；再从未学过的卡里按领域随机补足（排除已到期复习卡）。用户改领域或每日条数后快照作废重建。

### D-005 完成口径：跟读 + 应答都完成才算一条

- **日期**：2026-09-11
- **背景**：原实现只要产生过进度记录（即完成跟读）就计入「已完成」，进度虚高；复习卡因为带着上一次学习的分数，一进页面就显示「跟读 ✓ 应答 ✓」。
- **决策**：`已完成 = 跟读分与应答分都存在，且本轮提交发生在今天`。步骤标记同样只看今天的提交。

### D-006 复习排期一次只推进一级

- **日期**：2026-09-11
- **背景**：跟读与应答分两步提交，原实现两步各自触发一次排期计算，一次复习会让卡片连跳两个遗忘曲线阶段（S2 → S4）；且排期依据取跟读/应答较大值，与 PRD 口径不符。
- **决策**：排期只在「整卡完成」（应答打分）时推进一次；依据**综合分**（跟读 × 0.5 + 应答 × 0.5），阈值 `PASS_THRESHOLD = 85`。
- **影响**：跟读阶段只记分不改排期；中断在跟读阶段的复习卡仍保持到期，会重新出现在今日任务里。

### D-007 录音回听用本地 object URL 并交接给结果页

- **日期**：2026-09-11
- **背景**：用户可以录音但无法回听，`useRecorder.stop()` 拿到的音频 blob 被直接丢弃。
- **决策**：录音结束后生成 `objectURL` 供页面回放（播放/暂停，暂停回起点）；跳转结果页时把该 URL **交接**过去（交接后不在学习页卸载时回收），使用户能对照 AI 反馈复听；重新录音时回收上一段。回放与浏览器 TTS 互斥，避免叠音。
- **影响**：音频的**持久化**是另一个问题，见 D-017。

### D-008 跟读评分 100% 由词级相似度决定

- **日期**：2026-09-11
- **背景**：原跟读分只由录音时长推算（越接近「标准时长」分越高）再加 ±6 分随机抖动，**与用户实际说了什么完全无关**；反馈文案是拿分数套模板生成的。
- **决策**：按 PRD 06 章口径，跟读分完全由 ASR 转写与原句的词级相似度决定（权重 100%）：归一化 → LCS 词级对齐 → `相似度 = 正确词数 / 原句词数` → `分数 = clamp(round(52 + 相似度 × 46), 40, 98)`。反馈必须由 diff 生成。
- **影响**：**没有 ASR 就没有跟读分**（不得用随机数顶替），按 09 章降级为「只记完成、不打分」。这条使 D-013 成为 P2 的硬前提。

### D-009 学习页回显 ASR 转写并逐词对照

- **日期**：2026-09-11
- **背景**：用户希望知道「自己说的内容转成英文文本后是否正确」——这是区分「识别错」与「自己读错」的唯一依据。
- **决策**：录音结束后展示「我听到的」卡片：转写全文 + 转写来源标识 + 逐词对照原句（错误词红色波浪线，悬停显示被听成了什么）+ 词级准确度百分比。情境应答无唯一原文，只回显文本。转写失败按 09 章降级，**不允许用本地模拟文本顶替**。
- **影响**：跟读评测接口必须返回 `transcript` / `transcriptSource` / `alignment` / `similarity`；对齐算法在后端实现，前端只渲染。

### D-010 移除全部 mock 数据，按 PRD 做真实实现

- **日期**：2026-09-11
- **背景**：当前工程没有任何后端：登录态、内容库、进度、排期、评分、转写全部由 localStorage 与前端模拟逻辑提供。仅能演示，不可用。
- **决策**：**彻底移除所有 mock**。按 PRD 08 章实现真实架构：Supabase（Auth + Postgres）+ NestJS 后端 + Prisma，前端不再包含任何假数据、假延迟、假分数、假转写。
- **影响**：涉及前后端数据层重写，分 P1–P4 实施。

### D-011 ASR 与 LLM 只在后端调用

- **日期**：2026-09-11
- **背景**：前端曾用浏览器 `SpeechRecognition` 获取转写，并用本地模拟转写兜底。既不符合 PRD 06 章的评测链路（ASR 在后端），也无法保证一致性与可审计性；浏览器识别在部分网络环境不可用。
- **决策**：前端只负责采集音频并上传；ASR 与 LLM 均由 NestJS 后端调用，供应商以 `AsrProvider` / `LlmProvider` 接口注入。前端删除 `useTranscriber`，模拟转写与错词表一并删除，词级对齐算法下沉后端。
- **影响**：供应商密钥不进入前端；切换供应商不影响业务逻辑。

### D-012 LLM 供应商选定 DeepSeek

- **日期**：2026-09-11
- **状态变更**：原为待确认（D-012），用户于本轮确认选定 DeepSeek，转入已定。
- **背景**：PRD 06 章要求「统一接入国内大模型服务商，做成可替换供应商接口」，用于**情境应答的四维语义评测**与**内容生成**。
- **决策**：LLM 层使用 **DeepSeek**（OpenAI 兼容接口，`base_url = https://api.deepseek.com`）。模型名走环境变量配置，默认 `deepseek-chat`（稳定别名，指向当前最新对话模型），可切 `deepseek-reasoner` 等。
- **影响**：
  - DeepSeek 官方 API **不提供语音能力**（无 ASR、无 TTS，多模态仅支持图片输入）。因此 ASR 必须另选供应商 → 见 D-013；参考音频若需服务端合成 → 见 D-016。
  - 「内容生成与语义评测共用同一供应商」这条 PRD 要求**在 LLM 层面成立**（都用 DeepSeek），ASR 本就是另一路，不冲突。
  - 密钥 `DEEPSEEK_API_KEY` 只存在于后端环境变量，绝不进前端。

### D-014 仓库结构采用 monorepo

- **日期**：2026-09-11
- **状态变更**：原为待确认，用户于本轮确认采用 A 方案并接受搬迁。
- **背景**：加入 NestJS 后端后需要重新组织仓库；前后端共用类型（`ScenarioCard` / `UserProfile` / `TodayCard` / `RepeatScore` / `AnswerScore` / 评测契约）是这个项目的刚需。
- **决策**：采用 **npm workspaces monorepo**（不引入 pnpm 等新工具，npm 11 原生支持）：

  ```
  dailyspeak/
  ├─ apps/web/          前端（Vite + React + TS + Tailwind）
  ├─ apps/api/          后端（NestJS + Prisma）
  ├─ packages/shared/   前后端共用类型与常量
  ├─ docs/              需求 / 决策 / 待办
  ├─ design/            设计稿（项目级参考）
  └─ tools/             本地验证脚本
  ```

- **影响**：现有前端目录需整体搬迁到 `apps/web/`；根 `package.json` 改为 workspace 编排；`tsconfig` / `vite.config.ts` / Tailwind 扫描路径需同步调整。共用类型的唯一来源是 `packages/shared`，杜绝前后端类型漂移。

### D-027 今日快照的生成口径：复习卡不截断

- **日期**：2026-09-11
- **背景**：PRD 5.3 说「新句卡数量 = 用户每日条数 − 今日到期复习卡数（不为负）」，5.5 又说「到期卡计入当天复习卡，并受每日总条数约束」——两句话读起来冲突：**复习卡超过每日条数时，到底截不截断？** 后端要落库，必须先定死。同时 `GET /api/today` 是 GET 却会写库，并发首次进入可能重复生成快照。
- **决策**：
  1. **复习卡不截断**，到期多少张就进多少张；新句名额 = `max(0, 每日条数 − 到期复习卡数)`。今日总条数允许**超过**每日条数。
  2. 未完成首次引导（`domains` 为空）时**不对领域设限**，全部已上线内容都可推，且不算跨领域补齐。
  3. 快照生成**幂等**：靠 `today_plan` 唯一键 `(user_id, date_key)` 兜底，并发时后到的请求捕获 `P2002` 后读回已生成的那份。
  4. `contentWarning` **不落库**，读回快照时用同一纯函数从 `tasks` 复现，避免两份真相。
- **理由（为什么不截断）**：截断会让到期卡继续往后拖，遗忘曲线的间隔就不成立了——「该复习的时候没复习」正是这个产品要解决的问题。宁可一天多做几张。
- **影响**：
  - 学习台进度分母可以大于每日条数，UI 需按实际条数展示（`dailyCount` 随响应返回，便于解释）。
  - `today_plan.tasks` 的 Json 里多存了 `domain` 与 `fromFallback` 两个字段（原设计只有 `cardId`/`type`），用于复现告警与调试。

### D-028 连续学习天数：今天没学从昨天往前数

- **日期**：2026-09-11
- **背景**：原实现从「今天」开始往前连续计数。用户连续学了 6 天，第 7 天早上打开应用时今天还没学，界面直接显示「连续 0 天」——把昨天为止的成绩抹掉了。

### D-029 历史统计在应用层按本地日期归并

- **日期**：2026-09-11
- **背景**：连续天数需要「用户有提交的全部日期」。可选：① 在 SQL 里 `date_trunc('day', done_at)` 分组；② 取回 `done_at` 单列后在 Node 里按本地日期归并。另外「最近练习」的分数该展示什么也需要定死。
- **决策**：
  1. 采用 ②。SQL 的 `date_trunc` 按**数据库时区**算，与应用时区不一致时会算错日期；「本地日期」只能由运行时决定，所以在应用层归并。SQL 侧的区间过滤（本月 / 本周）用本地时间边界传参，走 `(user_id, done_at)` 索引。
  2. **本月卡片 / 累计卡片用 `count()`**，不把全部行读进内存；只有连续天数需要 `done_at` 单列全量。
  3. 「最近练习」的 `score` 只取**综合分 `composite`**；未完成或降级则为 `null`，前端显示「未打分」。**不得**用跟读分或 `0` 顶替（PRD 09 / D-010）。
- **影响**：
  - MVP 量级（单用户百行内）完全够用。**已知上限**：用户记录到万级时全量取 `done_at` 会变慢，届时应改写入一张 `study_days(user_id, date_key)` 汇总表——在需要之前不做（YAGNI）。
  - 旧实现 `composite ?? repeatScore ?? 0` 会给出 0 分的假成绩，本次一并修正。

### D-030 统一错误格式与请求日志

- **日期**：2026-09-11
- **背景**：S2 之前错误响应是 Nest 默认的 `{ message, error, statusCode }`，前端拿到校验失败只能显示一整串英文，无法按字段高亮。同时没有任何请求日志，出问题只能靠猜。
- **决策**：
  1. **成功响应不加 envelope**，直接返回资源本身；**只有错误**统一为 `{ code, message, details? }`（`ApiErrorBody`）。
  2. 用全局 `AllExceptionsFilter` 兜住所有异常：`HttpException` 按状态码映射 `code`；ValidationPipe 用自定义 `exceptionFactory` 产出字段级 `details`（键为字段名，嵌套用 `parent.child`）；Prisma 已知错误码 `P2025 → 404`、`P2002 → 409`、`P2003 → 400`；其余一律 500。
  3. **5xx 不外泄内部信息**（可能含 SQL 片段或密钥），完整堆栈只进服务端日志；非生产环境把真实原因放进 `details.detail` 方便本地排查。
  4. 全局 `LoggingInterceptor` 每请求一行：方法、路径、状态码、耗时、用户 id。
- **影响**：
  - 前端可以按 `code` 分支、按 `details` 高亮字段，不再解析文案。
  - **不记录请求体与响应体**：里面有录音 base64 和转写文本，全量打印会打爆日志。需要排查时按需临时加。
  - 4xx 只记一行 `WARN`，5xx 记完整堆栈，避免正常业务拒绝刷屏。
  - 业务代码用 `common/api-errors.ts` 的 `notFound()/badRequest()/conflict()/forbidden()` 抛出，不直接拼 HTTP 细节。

### D-031 内容不足时的跨领域补齐顺序与告警

- **日期**：2026-09-11
- **背景**：PRD 09 只说「内容某领域无卡可推 → 从其他已选领域补充，保证每日条数不中断；后台提示内容告警」。没说补齐顺序，也没说告警长什么样；实现时若依赖数据库返回顺序，同一份内容池会得到不可复现的结果，没法写测试。
- **决策**：
  1. 补齐顺序固定为：① 只完成跟读的卡（按完成时间升序）→ ② 已选领域内没学过的卡（**无偏**随机）→ ③ 其他有内容的领域（**首发领域优先，其余按字典序**，无偏随机）。
  2. 随机用 **Fisher-Yates**。原实现 `sort(() => Math.random() - 0.5)` 的分布是偏的，靠前的卡会长期更容易被推到。
  3. 告警分两种文案（凑不满名额 / 用了跨领域补齐），随 `GET /api/today` 的 `contentWarning` 下发，前端原样展示；同时在服务端打 `WARN` 日志作为内容管道的补充信号。
- **影响**：
  - 所有补齐规则是**纯函数**（`today.plan.ts`），注入固定随机源即可得到确定结果，已覆盖单测。
  - 首发领域（计算机/IT、职场通用）之外的领域一旦有了内容，会自动进入补齐候选，不需要改代码。

- **日期**：2026-09-11
- **背景**：腾讯云一句话识别**不接受 webm**，而 Chrome 的 MediaRecorder 默认录的就是 webm。同时 PRD 09 要求「校验格式与大小上限，超限直接拒绝」。问题是：在哪儿校验、以什么为准。
- **选项**：① 允许列表放宽到 webm，服务端装 ffmpeg 转码；② 前端在浏览器里转成 16k 单声道 WAV，服务端只收这一种格式。
- **决策**：选 ②，并且**服务端自己解析 WAV 头**得出时长与格式，**不信客户端上报的 `durationMs`**。
- **理由**：
  - ①要在服务器上多一个 ffmpeg 依赖与一整套转码运维，为了兼容一个我们自己能控制的客户端，不划算。
  - 时长窗口（跟读 3–15s、应答 30–60s）是**准入条件**，客户端随手写个数字就能绕过去；格式不对要到调用腾讯云时才报错，白费一次往返和一次配额。
- **踩到的坑（已修）**：第一版解析器按固定下标硬读 `data` 在偏移 36。但 WAV 是**分块格式**，`fmt ` 之后允许有别的块，`fmt ` 本身也有 16 / 18 / 40 字节多种长度。Windows SAPI 生成的 WAV 用 18 字节 `fmt `，`data` 落在偏移 38，直接被误判成「缺少 data 块」。现在改成逐块遍历（并按 RIFF 规范处理奇数字节的补齐位），同时保留严格性：必须是 RIFF/WAVE、必须未压缩 PCM、必须有 fmt 与 data、声明长度必须与实际字节对得上。
- **影响**：`AUDIO_LIMITS.allowedMimeTypes` 收窄为 wav 三种写法，`maxBytes` 降到 5MB（60 秒 16k 单声道实测约 1.9MB）。测试音频生成脚本也要按同样的分块方式算时长，否则会算出天文数字（同样踩过）。

### D-037 第三方失败降级：只记完成不打分，不新增字段

- **日期**：2026-09-11
- **背景**：PRD 09 要求第三方超时/失败时「降级为仅记已完成、不产生打分」，且「不允许用模拟文本或随机分数顶替」。实现上要么给 `user_progress` 加 `repeat_degraded` / `answer_degraded` 两个布尔字段，要么用别的办法表达。
- **决策**：**不加字段。** 降级 = `user_progress` 里存在该行、`done_at` 已更新、但对应分数为 `null`。行为上按「**未完成、待重测**」处理。
- **理由**：加字段要迁移，而它带来的唯一差别是「应答步降级后，学习台要不要显示应答已完成」。答案是**不该显示**——PRD 要求「引导用户稍后重测」，把降级标成「已完成」反而劝退了重测。于是这个字段没有存在价值。
- **影响**：
  - 降级卡片不会进入「已掌握」，下次排卡时会重新推给用户；只做了跟读的卡走 `inProgress` 优先补回。
  - 历史页把这类记录显示为「**未打分**」（`composite` 为 null），绝不显示 0 分——这条在 P1 S4 已实现，P2 的降级路径复用它。
  - **不会用降级覆盖已有分数**：上一次拿到 88 分，不能因为这次第三方挂了就被抹成 null（`update` 只动 `doneAt` / `mode`）。
  - 接口上 `score` 类型变为 `number | null`，并加 `degraded: boolean`，前端必须显式处理。

### D-038 复习排期同一天只推进一次

- **日期**：2026-09-11
- **背景**：D-006 规定「一次练习会话只推进一个阶段」，那是指跟读 + 应答两步不能各推进一次。但还有一个没覆盖的漏洞：**用户对同一张卡反复点「再次练习」**，每完成一次就推进一级，一天就能把 S1 一路推到 S6，遗忘曲线直接失效。
- **决策**：整卡完成时，**只在当前排期已到期（或还没有排期）时才推进**；未到期就只记进度，不动排期。判据直接复用排期算法里的纯函数 `isDue`。
- **影响**：
  - 同一天重复练习同一张卡：分数会更新（最后一次为准），但 `stage` 与 `due_at` 不变，`times_reviewed` 也不涨。
  - 学习模式（`new` / `review`）用同一个判据判定，避免两处口径打架：一张**刚学完、次日才到期**的新卡，当天再练一次仍记为新卡，不会被误记成复习。
  - 已加进端到端断言（`score-e2e` 的「再次完成整卡不会连跳阶段」）。

### D-039 DeepSeek 实际模型名与推理模型的 max_tokens 陷阱

- **日期**：2026-09-11
- **背景**：D-012 当时写的是用 `deepseek-chat`。P2 实测发现**这把 key 上根本不存在这个模型**：`GET /v1/models` 只返回 `deepseek-flash` 与 `deepseek-v4-pro`。
- **决策**：模型取 `.env` 的 `DEEPSEEK_MODEL`，当前值 `deepseek-flash`（用户自己填的）。评测请求 `temperature: 0`。
- **另一个必须写下来的坑**：这两个模型都是**推理模型**，`max_tokens` **同时**约束推理与正文。
  - 实测：`max_tokens: 8` 时返回 **HTTP 200 但 `content` 是空串**，`reasoning_tokens: 8`——看起来像密钥或网络问题，其实预算被推理吃光了。
  - 所以：默认 `max_tokens` 给到 1500，并且**把空正文当成失败抛出去**（抛错会触发重试，比静默产出 0 分安全）。供应商自检脚本里也因此不能用小值测「回一个词」。
- **`temperature: 0` 的理由**：用户对分数稳定性很敏感（「我说的一样，怎么这次少了 6 分」）。但实测同一段回答重复评测仍会有 ±2 分上下的波动（推理模型的固有不确定性），所以端到端断言用的是「波动在 ±10 分内」而不是严格相等。
- **实测数据**（6.3 秒跟读 + 34 秒应答）：ASR 约 620–740ms；LLM 四维评测约 2.9–3.8s。

### D-040 第三方重试口径：最多尝试 3 次

- **日期**：2026-09-11
- **背景**：PRD 09 原文是「自动重试 3 次」。这句话有两种读法：总共尝试 3 次，还是失败后再试 3 次（共 4 次）。
- **决策**：**总共最多尝试 3 次**（首次 + 2 次重试），指数退避 300ms → 1200ms。并把这句写进 PRD，消除歧义。
- **理由**：4 次尝试配上退避，最坏要等 6 秒以上，用户盯着转圈不划算；而两次重试已经能覆盖绝大多数的瞬时抖动。
- **影响**：耗尽后**把最后一次的错误抛出去**，由调用方决定降级还是 500 —— 重试本身不吞异常。`MAX_ATTEMPTS` 是导出常量，单测直接断言次数与退避序列。

### D-041 前端音频转码与它的测试策略

- **日期**：2026-09-11
- **背景**：`apps/web` 以前没有任何测试运行器；而这段转码逻辑一旦错了，现象是「上传成功但识别不出内容」，很难查。同时重采样质量直接影响识别率（腾讯是按字收费的，识别不准等于白花钱）。
- **决策**：
  1. 转码落在 `apps/web/src/utils/wav.ts`：`decodeAudioData` → 降混单声道 → 重采样到 16k → 编码 44 字节头 PCM WAV。
  2. **重采样优先交给 `OfflineAudioContext`**（浏览器自带的重采样质量比手写好），只在它不存在或构造失败时才回退到自写的 `resampleLinear`。
  3. 前端接入 **vitest**（`vitest@^2.1.9`）。**版本必须钉在 2.x**：vitest 5 要求 vite ≥ 6，而本项目在 vite 5 上；这与 D-023 的版本锁定是同一个理由。
  4. 单测覆盖纯函数（降混、WAV 头字段、线性重采样），**外加一组用 `vi.stubGlobal` 造假 Web Audio 的桩测试**覆盖「走浏览器重采样 / 回退 / 解码失败」三条分支。
- **一个值得记下的过程**：桩测试的第一版是**空断言**——桩用常量电平，两条重采样路径产出的字节完全相同，把实现改成「永远走回退」测试依然全绿。做了变异测试才发现。修正办法是让桩渲染方波、并逐字节比对期望值（期望值由 `encodeWavPcm16` 对同一份样本编码得出，不手写量化规则）。**测试写了不等于测到了。**
- **影响**：根 `npm test` 现在跑 api + web 两个套件；`test:api` 可单独跑后端。

### D-013 ASR 供应商选定腾讯云语音识别

- **日期**：2026-09-11
- **状态变更**：原为待确认，用户于本轮确认选用**腾讯云语音识别（ASR）**，转入已定。
- **背景**：按 D-008，跟读分完全依赖 ASR 转写质量。用户选定 LLM 用 DeepSeek（D-012），但 **DeepSeek 官方 API 没有任何音频接口**，ASR 必须独立选型。用户选择腾讯云因其每月有免费额度。
- **决策**：ASR 使用**腾讯云语音识别**，走「**一句话识别**」接口 `SentenceRecognition`（`asr.v20190614`，同步返回），SDK 用 `tencentcloud-sdk-nodejs-asr`。
- **接口参数**（依据官方 SDK 类型定义 `asr_models.d.ts` 核实）：

  | 参数 | 取值 | 说明 |
  | --- | --- | --- |
  | `EngSerViceType` | `16k_en` | 英语引擎。本项目内容全为英文跟读。中文可用 `16k_zh`，中英粤混用用 `16k_zh-PY` |
  | `SourceType` | `1` | 语音数据走 post body（base64） |
  | `VoiceFormat` | `wav` | **见下方格式约束** |
  | `Data` | base64 | 时长 ≤ 60s，Base64 后 ≤ 3MB |
  | `ProjectId` / `SubServiceType` / `UsrAudioKey` | 已废弃 | 仍可传，填 0 / 2 / 任意串 |

- **⚠️ 关键约束：腾讯云不接受 webm**。官方支持的 `VoiceFormat` 为 **wav、pcm、ogg-opus、speex、silk、mp3、m4a、aac、amr**，而浏览器 `MediaRecorder` 在 Chrome/Edge 上默认输出 `audio/webm;codecs=opus`（实测 Chrome 支持 webm 与 mp4/AAC，**不支持 ogg**）。因此上传前必须转换。
- **决策：前端转成 16kHz 单声道 16-bit PCM WAV 再上传**。理由不只是格式兼容——`16k_en` 引擎本身期望 16kHz 输入，而 MediaRecorder 的默认采样率是 48kHz；重采样到 16k 同时解决兼容性与识别准确率。本地回听仍用原始录音 blob（音质更好，且零延迟）。
- **影响**：
  - 前端需要新增「解码 → 重采样到 16k → 编码 WAV」工具（纯函数，可单测），不能把 webm 直接丢给腾讯。
  - 60s 应答的 16k 单声道 WAV ≈ 1.92MB，base64 后 ≈ 2.56MB，**逼近 3MB 上限**（约 85%），前后端都要做时长与体积双校验。
  - 密钥 `TENCENT_SECRET_ID` / `TENCENT_SECRET_KEY` 仅存后端环境变量。
- **待你确认（不阻塞实现）**：你提到的免费额度页里列的是「**录音文件识别**」与「**实时语音识别**」。我实现的是「**一句话识别**」，三者是不同子产品、免费额度与计费口径可能不同。**请在腾讯云控制台确认「一句话识别」是否也有免费额度**；若你的免费额度只覆盖「录音文件识别」，我改用异步接口 `CreateRecTask` + `DescribeTaskStatus`（同一 `AsrProvider` 接口下换实现即可，但需要轮询，单次评测时延会从 ~1s 变成 ~3-5s）。
